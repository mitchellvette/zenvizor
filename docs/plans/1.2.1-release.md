## Character of the release

1.2.1 is a maintenance patch. It bundles the accumulated hygiene work since 1.2.0
plus one substantive-but-invisible change (the `System.CommandLine` migration).
The rules for a `1.x.y` bugfix release apply (see `docs/versioning.md`):

- No behaviour changes that surprise users.
- No new user-visible features.
- Existing installations upgrade in place with no user-visible surface change
  beyond the fixes / hardening themselves.
- `zvctl` verbs, flags, exit codes, and output formats are unchanged (this is
  binding for the `System.CommandLine` migration).
- IPC contract is unchanged; DB schema is unchanged; config layout is unchanged.

This release does **not** include any post-MVP Epic work from
`docs/roadmap/` — no epic work has landed since 1.2.0.

## System.CommandLine beta4 → 2.0 stable — migration plan

### Motivation

- **Current:** `System.CommandLine 2.0.0-beta4.22272.1`, pinned in
  `Directory.Packages.props`. Published mid-2022; frozen at a preview API.
- **Target:** `System.CommandLine 2.0.9` — stable, shipping as part of the
  .NET 10 release train via the .NET VMR (Version Master Repo). Officially a
  Microsoft-shipped library aligned with the SDK we're already on.
- **Why now:** the ignore rule buys quiet, not a fix. Preview-lib exposure on
  the CLI is technical debt that grows every SDK release. The stable API is
  final and won't churn again inside 2.x.
- **Bonus, deliberately not exercised in this release:** the stable API
  surfaces a real `CancellationToken` in handler signatures. Wiring it into
  actual work is a separate change (see "Non-goals").

### Scope

- **Files touched:** exactly two.
  - `src/ZenVizor.Cli/Program.cs` (~1,026 lines; ~62 use sites of
    `RootCommand` / `Command` / `Option` / `Argument` / `SetHandler` /
    `AddOption` / `AddArgument` / `AddCommand` / `AddValidator` /
    `ParseResult.GetValueForOption` / `ParseResult.GetValueForArgument`).
  - `.github/dependabot.yml` — remove the `System.CommandLine` ignore entry
    added in #16 (same commit as the package bump, per the note in the ignore
    comment itself).
- **Package pin:** update `Directory.Packages.props` — the exact target is
  `2.0.9` if it's still current when the migration lands; otherwise the latest
  `2.0.x`.

### Current-state API patterns (from `Program.cs`)

Extracted directly from the file to make the mapping concrete. All beta4:

```csharp
// Root + subcommand
var root = new RootCommand("zvctl — ZenVizor CLI client.");
var pingCommand = new Command("ping", "…");
root.AddCommand(pingCommand);

// Handler — no options / arguments
pingCommand.SetHandler(async ctx => ctx.ExitCode = await RunPingAsync());

// Option with aliases + default
var windowOption = new Option<string>(
    aliases: new[] { "--window", "-w" },
    description: "…",
    getDefaultValue: () => "24h");

// Option with validator
topOption.AddValidator(result =>
{
    if (result.GetValueOrDefault<int>() < 0)
        result.ErrorMessage = "--top must be zero or positive.";
});

// Argument
var appIdArg = new Argument<int>("appId", "App id (see `zvctl apps`).");

// Attach + handler with values
appCommand.AddArgument(appIdArg);
appCommand.AddOption(windowOption);
appCommand.SetHandler(async ctx =>
{
    var id = ctx.ParseResult.GetValueForArgument(appIdArg);
    var w  = ctx.ParseResult.GetValueForOption(windowOption)!;
    ctx.ExitCode = await RunAppAsync(id, w);
});
```

### Target-state API patterns (stable 2.0.x)

```csharp
// Root + subcommand (same shape)
var root = new RootCommand("zvctl — ZenVizor CLI client.");
var pingCommand = new Command("ping", "…");
root.Subcommands.Add(pingCommand);

// Handler — returns int (or Task<int>)
pingCommand.SetAction(async (parseResult, ct) => await RunPingAsync());

// Option — name-first ctor, aliases via Aliases property, default via factory
var windowOption = new Option<string>("--window", "-w")
{
    Description = "…",
    DefaultValueFactory = _ => "24h",
};

// Option with validator (Validators.Add + AddError, not ErrorMessage=)
topOption.Validators.Add(result =>
{
    if (result.GetValue(topOption) < 0)
        result.AddError("--top must be zero or positive.");
});

// Argument (same shape; Description via property)
var appIdArg = new Argument<int>("appId") { Description = "App id …" };

// Attach — collection properties instead of Add* methods
appCommand.Arguments.Add(appIdArg);
appCommand.Options.Add(windowOption);

// Handler — ParseResult + CancellationToken, returns int directly
appCommand.SetAction(async (parseResult, ct) =>
{
    var id = parseResult.GetValue(appIdArg);
    var w  = parseResult.GetValue(windowOption)!;
    return await RunAppAsync(id, w);
});
```

### Mechanical translation table

| beta4                                                | 2.0 stable                                            |
| ---------------------------------------------------- | ----------------------------------------------------- |
| `using System.CommandLine.Invocation;`               | *remove* (no `InvocationContext` in 2.0)              |
| `Command.AddCommand(cmd)`                            | `Command.Subcommands.Add(cmd)`                        |
| `Command.AddOption(opt)`                             | `Command.Options.Add(opt)`                            |
| `Command.AddArgument(arg)`                           | `Command.Arguments.Add(arg)`                          |
| `Command.SetHandler(async ctx => …)`                 | `Command.SetAction(async (parseResult, ct) => …)`     |
| `ctx.ParseResult.GetValueForOption(opt)`             | `parseResult.GetValue(opt)`                           |
| `ctx.ParseResult.GetValueForArgument(arg)`           | `parseResult.GetValue(arg)`                           |
| `ctx.ExitCode = X; return;`                          | `return X;` (handler returns `int` / `Task<int>`)     |
| `new Option<T>(aliases: [...], description: "…")`    | `new Option<T>("--name", "-n") { Description = "…" }` |
| `new Option<T>(..., getDefaultValue: () => v)`       | `new Option<T>(...) { DefaultValueFactory = _ => v }` |
| `opt.AddValidator(r => r.ErrorMessage = "…")`        | `opt.Validators.Add(r => r.AddError("…"))`            |
| `result.GetValueOrDefault<T>()`                      | `result.GetValue(opt)` / `result.GetValue(arg)`       |
| `new Argument<T>(name, description)`                 | `new Argument<T>(name) { Description = description }` |

### Semantic differences (not just renames)

These are the real risk surface — read carefully during review.

- **Exit codes.** The obsolete-comment on `Program.cs:20-23` warns that setting
  `Environment.ExitCode` doesn't propagate through `RootCommand.InvokeAsync`
  and that handlers must set `ctx.ExitCode`. In the 2.0 API the handler
  **returns** the exit code directly, and the return value flows through
  `parseResult.InvokeAsync()` → the process exit code. The whole class of "I
  set ExitCode and it silently didn't stick" bug is structurally impossible in
  the new API. **The `// IMPORTANT: handlers MUST set context.ExitCode …`
  comment block becomes obsolete; delete it in the migration** rather than
  updating it — the new pattern is self-evident.
- **Cancellation.** New handler signature is
  `(ParseResult parseResult, CancellationToken ct)`. The `ct` fires when the
  process is being terminated (Ctrl-C, `dotnet` cancellation). **We do not
  plumb `ct` into IPC calls in this migration** — that is a separate
  change. Handlers accept the token and ignore it. Explicit `ct` parameter is
  fine (documents intent); `_` is also fine.
- **Help output.** Formatting of `zvctl --help` and `zvctl <cmd> --help` may
  change slightly (spacing, arity display, order of `--help`/`--version`).
  No automation should be scraping this output. Sanity-check that the verbs
  and descriptions are still present and legible.
- **Parse errors.** Error message wording for parse failures (unknown option,
  missing required argument) will differ. Exit-code 1 for parse failure is
  preserved by the new parser by default; verify.
- **`InvokeAsync` on `RootCommand`.** The invocation surface renamed:
  historically `RootCommand.InvokeAsync(args)`; in 2.0 the common pattern is
  `root.Parse(args).InvokeAsync()`. Same net effect. Migrate the
  bottom-of-file `return await root.InvokeAsync(args);` line accordingly.

### Non-goals for this migration

Explicitly out of scope. If you find yourself doing any of these, stop —
they're separate PRs / releases.

- Wiring `CancellationToken` into IPC calls, `Task.Delay`s, or any actual
  work. Handlers accept the token and don't use it. Cancellation plumbing is
  a design-and-test exercise on its own; not this PR.
- Adding new commands, options, or arguments.
- Renaming existing commands, options, arguments, or aliases.
- Changing any output format (`--json` envelopes, table columns, exit codes).
- Bumping `IpcSchemaVersion` — no IPC surface change.
- Migrating tests away from FluentAssertions (separate track).
- Any UI (WPF) work.

### Test strategy

Headless-first per `CLAUDE.md`:

- `dotnet build ZenVizor.slnx -c Release --no-restore` — zero warnings, zero
  errors.
- `dotnet test ZenVizor.slnx -c Release --no-build` — green. There are no
  existing unit tests specifically for `zvctl` parsing; the CLI is exercised
  by manual verbs against a running service.

Manual verbs (against a running dev service — start via `install-dev.ps1`
per `CLAUDE.md`'s service-lifecycle notes):

- [ ] `zvctl` (no args) → prints help, exit 0.
- [ ] `zvctl --help` → prints all verbs, exit 0.
- [ ] `zvctl ping` → prints `pong` (or the equivalent handshake summary),
      exit 0.
- [ ] `zvctl status` → prints service status, exit 0.
- [ ] `zvctl stats` → prints capture-pipeline counters, exit 0.
- [ ] `zvctl snapshot` → top-10 apps table, exit 0.
- [ ] `zvctl snapshot --all` → all apps with non-zero bytes.
- [ ] `zvctl snapshot --json` → valid JSON envelope; validate with
      `zvctl snapshot --json | ConvertFrom-Json`.
- [ ] `zvctl apps -w 24h -n 10` → table, exit 0.
- [ ] `zvctl apps -w 7d --top 5 --json` → JSON envelope.
- [ ] `zvctl app <id>` (pick a real id from `zvctl apps`) → detail, exit 0.
- [ ] `zvctl app 999999` → not-found path (exit code documented; verify
      preserved).
- [ ] `zvctl report …` → happy path, exit 0.
- [ ] **Negative — parse error:** `zvctl unknown-verb` → exit **1**.
- [ ] **Negative — validator:** `zvctl apps --top -1` → exit **1** with
      message `--top must be zero or positive.` (validator still fires,
      wording preserved).
- [ ] **Negative — IPC unreachable:** stop the service, `zvctl ping` → exit
      **3** (documented pipe-timeout exit code).
- [ ] **Negative — IPC schema mismatch:** simulated only if a stub is
      available; otherwise skip and document. Exit **2** on version-mismatch
      path per existing contract.
- [ ] `zvctl --version` (if present in beta4 output) → still works.

### Risk / rollback

- **Compile-error risk:** 62 sites migrated by hand. Bulk mechanical, low
  cognitive load per site, but easy to miss one. Mitigation: single PR,
  reviewed as one diff; `dotnet build` gates.
- **Behavioural drift risk:** the exit-code / handler-return semantic change
  is the most likely source of a subtle regression. Mitigation: the negative
  test cases above explicitly cover the exit codes 1 / 2 / 3 paths that the
  existing code carefully sets.
- **Rollback:** revert the merge commit. The `.github/dependabot.yml`
  ignore entry is restored by the same revert, so Dependabot goes quiet
  again. No user data / state is touched by this change; a rollback is a
  build-time-only concern.

### Approach — one PR

The beta4 and 2.0 APIs can't cleanly coexist inside a single `.cs` file
(namespace / type / member reuse would clash), so there is no risk-reducing
value in a staged, per-verb migration. Ship it as one PR against a
`feat/system-commandline-2.0` branch. Commit granularity inside the PR is up
to preference; a single commit is fine.

> First maintenance patch after 1.2.0. Small quality-of-life and security
> hardening, no user-visible feature changes.
>
> ZenVizor remains a lightweight, **passive** Windows network monitor: it
> attributes outbound and inbound traffic to the originating process
> (including svchost-hosted service names), stores tiered history locally in
> SQLite under user-configurable retention, surfaces a near-live dashboard
> with local alerts, produces daily reports, and emits **zero network traffic
> of its own**, verified end-to-end via the self-monitoring gate on every
> release.
>
> ## What's new in 1.2.1
>
> - **Security-hardened ETW parsing.** The kernel-network capture pipeline
>   picks up a batch of upstream bounds-checking fixes in the event-record
>   parser and TDH surfaces (Microsoft.Diagnostics.Tracing.TraceEvent

>   check event payloads that were previously assumed well-formed.
> - **Assorted upstream fixes.** Point-release bumps for the SQLite provider,
>   charting library, tray icon library, and logging abstractions. These are
>   fixes-only patches from the Microsoft .NET team and the underlying
>   library maintainers.

>   flag, exit code, or output-format change. `zvctl` behaves identically
>   to 1.2.0 from a user's perspective; internally, we moved off the
>   preview-branded 2022 API onto the stable Microsoft-shipped 2.0 API

>
> IPC contract is unchanged. DB schema is unchanged. Config layout is
