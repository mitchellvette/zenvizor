Second post-MVP feature release. Epic B — **Alert noise + gating** — corrects the day-one alert flood a fresh install used to produce, and gives you three per-severity desktop-notification toggles so you can pick exactly what level of interruption you want.

ZenVizor remains a lightweight, **passive** Windows network monitor: it attributes outbound and inbound traffic to the originating process (including svchost-hosted service names), stores tiered history locally in SQLite under user-configurable retention, surfaces a near-live dashboard with local alerts, produces daily reports, and emits **zero network traffic of its own**, verified end-to-end via the self-monitoring gate on every release.

## What's new in 1.2.0

- **No more first-day alert flood.** On a fresh install (or immediately after a Reset History) ZenVizor now treats every app already running on your machine as pre-existing rather than "newly installed". Chrome, Teams, svchost, and the dozens of other programs that talk to the network the moment capture starts no longer trip the "newly-installed program reached the network" alert. Critical signals — an unsigned program from a user-writable folder reaching the internet — keep firing throughout, even for apps that landed within seconds of ZenVizor.

- **A 48-hour settling window after install.** For the first two days after ZenVizor starts on a machine, any newly-observed app is assumed to be part of the initial software inventory and skips the first-run signal. After 48 hours, a genuinely new program that reaches out gets flagged normally — so a dropper installed on day three still surfaces.

- **Per-severity notification toggles.** Settings → Alerts now has three peer toggles — Critical / Warning / Info — instead of a single "Show desktop notifications" switch. The fresh-install default is Critical-only, which kills the toast storm without silencing the security-critical signal. Turn Warning or Info back on whenever you want the extra chatter; the Alerts page always lists everything ZenVizor noticed regardless.

- **Send test notification now respects your toggles.** The button under the toggles fires one sample notification per enabled severity — so you can visually confirm the exact set of toasts your current configuration would produce. Severities set to off stay silent, which is also positive verification that the gating is doing what it advertises.

- **1.1.x upgrade honours your prior notification choice.** If you had "Show desktop notifications" ON in 1.1.x, all three per-severity toggles land ON after upgrade, so you don't silently lose alerts you'd come to expect. If it was OFF, all three land OFF. Fresh installs get the Critical-only default.

## No breaking changes

The IPC settings contract gained three trailing per-severity fields; older clients that only read the legacy `ToastOnAlert` field continue to work — the server computes that value as the OR of the three new fields for back-compat. DB schema is unchanged (the two new baseline keys and three new toast keys sit in the existing key/value `settings` table). No config-layout change. `zvctl` is unchanged. Existing automation and data carry over without intervention. See [`docs/versioning.md`](https://github.com/mitchellvette/zenvizor/blob/v1.2.0/docs/versioning.md) for the policy.

## Upgrading from an earlier version (1.0.0, 1.1.0, or 1.1.1)

In-place upgrade. Download **`ZenVizorSetup.exe`** below and run it on a machine that already has an earlier version installed; Windows Installer will swap the installation in place (same `UpgradeCode`) and your existing `%ProgramData%\ZenVizor\zenvizor.db` history and settings carry forward unchanged. The service will restart as part of the upgrade; the UI re-launches automatically.

> **The 48-hour baseline window starts at first service run of 1.2.0** — not at your original install time. That means the first 48 hours after upgrading, first-run alerts are suppressed for every app on your machine. This is intentional: a 1.1.x upgrade doesn't distinguish between "app installed years ago" and "app installed yesterday" without a per-app scan, so the settling window covers both cases uniformly. Post-48-hour behaviour is identical to a fresh install.

## Install (new users)

Download **`ZenVizorSetup.exe`** below and run it. The bundle:

- Detects whether the .NET 10 Desktop Runtime is already installed; installs it silently (from the embedded payload) if missing.
- Installs the ZenVizor Windows Service, the WPF dashboard, and the `zvctl` CLI.
- Creates the data directory at `%ProgramData%\ZenVizor\`, ACL'd to SYSTEM + Administrators.

Total install footprint ≈ 55 MB under `%ProgramFiles%\ZenVizor\` (plus the shared .NET runtime in its standard location).

## System requirements

- Windows 10 or 11, x64.
- Administrator privileges to install (the service runs as `LocalSystem`); day-to-day UI use is non-elevated.

## Files in this release

- `ZenVizorSetup.exe` | the canonical install bundle (~74 MB; embeds the .NET 10 runtime for offline installability).
- `ZenVizor.msi` | the inner MSI for advanced users / silent deployment automation. Most users want the bundle.
- `SHA256SUMS.txt` | SHA256 hashes for the binaries above, attached for offline verification.

## Internal / dev-only notes

Not part of any shipped surface — collected here because they landed on the 1.2.0 branch:

- **`ZENVIZOR_DATA_DIR` environment variable** — overrides the service's data directory (default `%ProgramData%\ZenVizor\`) so a dev can point the service at a scratch dir without touching production data. Not documented in the installed help / man pages; dev-only.
- **`ZENVIZOR_DISABLE_CAPTURE` environment variable** — starts the service without wiring ETW / DNS / SNI capture or the retention purge, so it serves the existing database over IPC unchanged. Used by the demo-screenshot workflow. Dev-only.
- **`ZenVizor.SeedDemo` tool** — a dev-only CLI that populates a scratch database with realistic-looking traffic + alert history for marketing screenshots. Not shipped in the installer; lives under `tools/` in the source tree.
